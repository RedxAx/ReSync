## Concrete Current-System Traces

### Graph Open, Save, Mutation And Conflict

1. Remotely calls `ReSyncFlowClient.sendResourceSave` (lines 2987–3027). The frame contains a resource-specific packet byte, request ID, then serialized JSON. It does not send a generic typed locator envelope. For graphs, the serialized graph carries revision/hash fields if the client previously loaded them.
2. The server dispatches by resource-family packet routes: `FlowResourcePacketHandler.handleSave` lines 78–97 deserializes, validates, and invokes `FlowResourceRegistry.saveFromSession`; legacy graph packet path `FlowBlueprintPacketHandler.handleSave` lines 104–179 directly deserializes and saves.
3. `FlowBlueprintPacketHandler.handleSave` mutates incoming graph state (`setId`, `setResourceMutationId`), calls live `FlowGraphMigrator.migrateGraph` (line 132), validates, persists with `FlowStorage.saveGraph`, updates trigger bindings, publishes collaboration, then sends revision/hash ACK.
4. `FlowStorage.reloadGraph(type,id)` lines 168–196 reads a type-specific asset, deserializes, applies identity, validates, caches it by type+ID, and calls a graph-change listener. `saveGraph` lines 220–301 derives/infer type, reads existing revision/mutation ID, checks only a positive submitted revision against current revision (258–259), commits graph plus project metadata atomically (280–289), clears a separate tombstone, and then performs duplicate cleanup and cache notifications.
5. A conflict becomes `ResourceRevisionConflictException`. `FlowResourcePacketHandler` catches it at lines 111–117 and emits only an editor diagnostic instructing reload. The legacy graph handler catches it at 184–186 and only fails the job/logs. Neither trace sends the authoritative normalized payload/revision in that conflict response.
6. Client ACK processing (`ReSyncFlowClient.handleResourceSaveAck`, lines 2198–2263) marks a graph saved with revision/hash. On a normal resource-change event, client deserializes event payload into a resource-specific model and caches it; parse failure requests a single resource refresh (1679–1709). Event record fields are type, resource ID, payload, author, and changed timestamp: no revision, mutation ID, hash, server locator, or deletion revision.

Current defect: conflict recovery is instruction-based, not an authoritative refresh contract. An event has no ordering fields to prevent a late payload overwriting a later acknowledged mutation.

### Collaboration Patches And Disconnect/Reconnect Ordering

1. `FlowWorkspaceService.handleJoin` lines 63–90 resolves a workspace using `key(type,resourceId)`, registers session membership, and sends a document snapshot with workspace sequence and awareness.
2. `handleOperation` lines 107–161 validates patches, evaluates `(baseSequence,operationId)` through `WorkspaceRevision`, replays patches into a copied JSON object, records pending patches, advances a sequence, and broadcasts an operation. Duplicate operations replay the existing event; a sequence conflict emits only `Workspace Sequence Conflict` resync.
3. On a persisted resource change, `resourceSaved` lines 228–246 parses latest payload, rebases pending patches, and sends resync. `save` lines 248–275 serializes/submits a workspace-aware resource and clears pending patches after saving. This is distinct from ordinary resource mutation packet flows.
4. Remotely’s `ReSyncWorkspaceClient` applies server snapshots/operations to ReSyncCore `LiveDocumentChannel`; `LiveDocumentChannel.acceptSnapshot` rejects snapshots older than its tracked sequence and clears pending operations. This is the strongest current ordering evidence, but it is workspace-only and key remains string type+ID.
5. On WebSocket close/error, `ReSyncFlowClient` lines 543–587 marks authentication/registry unavailable, disconnects collaboration/workspaces, marks option catalogs stale, then schedules reconnect. After handshake, lines 895–909 subscribe channels, mark collaboration ready, call `workspaces.connect`, request node registry/jobs, flush pending sends, then invoke the connection listener. No evidence establishes a single global ordering between registry hydration, resource lists, queued mutations, resource-change events, and workspace snapshot.
6. Disconnected resource saves are retained as executable closures in `pendingSends` (lines 2997–3001) and later flushed after handshake (line 908). There is no demonstrated revalidation against newly hydrated revision before that send.

### Extension Add/Unload, Missing Extension And Client Fallback

1. An extension receives independent APIs for `registerNode`, `registerHandler`, type, conversion, option source, resource, and validator (`ReSyncExtensionContext.Registrations`, lines 52–84). `ReSyncExtensionManager.registerExtension` lines 160–178 inserts extension state, records metadata, then runs `initializeExtension`; a failure cleans up already-registered items.
2. Registry registration is mutable and per-definition. `NodeDefinitionRegistry.register` lines 33–49 overwrites an existing node ID from another plugin by removing its prior ownership and placing the new definition. `registerAll` loops one at a time. Thus collisions/order can alter active state before a contribution-wide rejection.
3. Unload (`ReSyncExtensionManager.unregister`, lines 203–215) stops extension then independently unregisters node definitions, runtime registry entries, handlers, properties, catalogs, types, conversions, resources, validators, providers, listeners, and modules (`cleanupState`, lines 225–305), then refreshes the node registry. No snapshot transaction/drain policy proves in-flight execution or existing graph data safety.
4. Client applies node registry snapshots in `ReSyncFlowClient.handleNodeRegistrySnapshot` lines 2322–2367. It writes unresolved plugin payloads to `NodeRegistryTombstoneCache`; that cache keys server → plugin ID. `loadCachedRegistry` lines 2595–2613 restores cached snapshot/unresolved plugins before live sync. This preserves some definition payload availability, not a demonstrated opaque persisted graph node/wire payload.
5. Compatibility checks (`compatibleRegistrySnapshot`, lines 2370–2389) reject snapshots outside hard contract range, mismatched server, or expiry via `protocolError`. The hard-coded capability list (line 133) contains `opaque_resources`, but no trace proves negotiation turns unsupported node/editor capability into read-only lossless graph material rather than rejection or client-specific fallback.

### Legacy Migration, Export/Import, Snapshot/Restore

- Legacy migration is definitely live: `FlowBlueprintPacketHandler.handleSave` calls `FlowGraphMigrator`; `FlowStorage.migrateLegacyAssets` calls metadata reconstruction, command reclassification, flow/resource migration, duplicate cleanup, and legacy directory scans. `FlowStorage` excludes internal `.snapshots`, `.quarantine`, `.tombstones`, and `.migrations` roots from normal asset discovery, but this is not a coordinated replacement snapshot system.
- Per-transaction asset recovery exists: `FlowStorage.previewAssetRestore` and `restoreAssetSnapshot` lines 153–162 delegate to `AssetTransactionManager`, clear caches, and reindex. Legacy flow-save compensation calls `restoreFlowSave`/`storage.restoreGraph`. These paths cover local mutation recovery, not full ReSync-folder restore with participants, manifest, fencing, build validation, journal states, or atomic activation.
- Search of the Flow/storage/module and ReSyncCore scopes found no generic graph export/import operation or complete snapshot/restore coordinator. Network/runtime snapshots and `AssetTransactionManager` snapshots are narrower concepts. This is recorded as absence, not inferred target behavior.
- `run/plugins/ReSync` was not copied or inspected beyond the pack’s documented read-only inventory. It is not a populated resource fixture and cannot evidence graph export/import or complete restore.
